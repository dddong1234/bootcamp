## 2. GitHub와 원격 저장소

GitHub는 Git 저장소를 온라인에 올려두고 관리할 수 있게 해주는 서비스다.

로컬 저장소가 내 컴퓨터 안에 있는 Git 저장소라면, 원격 저장소는 인터넷에 있는 Git 저장소다.

원격 저장소의 역할은 다음과 같다.

- 여러 사람이 같은 코드를 공유할 수 있다.
- 내 코드를 백업할 수 있다.
- 협업의 기준점이 된다.
- 팀원이 같은 프로젝트를 함께 관리할 수 있다.

GitHub에서 새 Repository를 만들면 원격 저장소 주소(URL)가 발급된다.  
이 주소를 로컬 Git 저장소와 연결하면 내 컴퓨터의 프로젝트를 GitHub에 올릴 수 있다.

원격 저장소를 연결하는 명령어는 다음과 같다.

```bash
git remote add origin 원격저장소_URL
```

연결된 원격 저장소를 확인하려면 다음 명령어를 사용한다.

```bash
git remote -v
```

## 3. git push와 git pull

로컬 저장소와 원격 저장소를 동기화할 때 주로 사용하는 명령어는 `git push`와 `git pull`이다.

### git push

`git push`는 로컬 저장소에 있는 커밋을 원격 저장소로 올리는 명령어다.

```bash
git push -u origin main
```

위 명령어는 로컬의 `main` 브랜치를 원격 저장소의 `main` 브랜치로 업로드한다.

처음 push할 때 `-u` 옵션을 사용하면 이후에는 더 간단히 `git push`만 입력해도 된다.

### git pull

`git pull`은 원격 저장소의 변경 사항을 내려받아 내 로컬 저장소에 반영하는 명령어다.

```bash
git pull
```

예를 들어 GitHub 웹에서 파일을 직접 수정했거나, 다른 팀원이 원격 저장소에 코드를 올렸다면 내 로컬 저장소에도 그 변경 사항을 가져와야 한다.  
이때 `git pull`을 사용한다.

정리하면 다음과 같다.

| 명령어 | 의미 |
|---|---|
| `git push` | 로컬 커밋을 원격 저장소로 업로드 |
| `git pull` | 원격 저장소의 변경 사항을 로컬로 가져오기 |

## 4. Clone과 Fork의 차이

GitHub 협업에서 자주 나오는 개념이 Clone과 Fork다.

둘 다 원격 저장소의 코드를 가져오는 것과 관련이 있지만, 목적이 다르다.

### Clone

Clone은 원격 저장소를 그대로 내 로컬 컴퓨터로 복사하는 것이다.

```bash
git clone 저장소_URL
```

Clone은 보통 같은 저장소에 push 권한이 있을 때 사용한다.  
팀 내부 협업에서 많이 사용된다.

예를 들어 팀 프로젝트 저장소에 collaborator로 등록되어 있다면, 해당 저장소를 clone해서 작업하고 다시 push할 수 있다.

### Fork

Fork는 다른 사람의 저장소를 내 GitHub 계정으로 복사하는 것이다.

원본 저장소에 직접 push 권한이 없을 때 사용한다.  
오픈소스 기여에서 자주 사용하는 방식이다.

Fork를 하면 내 GitHub 계정 아래에 원본 저장소의 복사본이 만들어진다.  
이후 내 저장소에서 작업한 뒤 Pull Request를 보내 원본 저장소에 반영을 요청할 수 있다.

| 구분 | Clone | Fork |
|---|---|---|
| 의미 | 원격 저장소를 로컬로 복사 | 다른 사람의 저장소를 내 GitHub 계정으로 복사 |
| 사용 상황 | 같은 저장소에 push 권한이 있을 때 | 원본 저장소에 직접 push 권한이 없을 때 |
| 주 사용처 | 팀 내부 협업 | 오픈소스 기여 |

## 5. Pull Request란?

Pull Request, 줄여서 PR은 내가 작업한 변경 사항을 원본 저장소에 반영해달라고 요청하는 것이다.

PR은 단순히 코드를 합치는 기능만이 아니라, 변경 내용을 설명하고 리뷰를 요청하는 협업 절차다.

Pull Request의 역할은 다음과 같다.

- 변경 내용을 설명한다.
- 팀원에게 리뷰를 요청한다.
- 병합 전에 코드를 검증한다.
- 코드 품질을 유지한다.
- 협업 과정의 기록을 남긴다.

예를 들어 `feature/login` 브랜치에서 로그인 기능을 개발했다면, 해당 브랜치를 `main` 브랜치에 병합해달라는 Pull Request를 만들 수 있다.

```text
feature/login → main
```

팀원은 PR을 보고 코드 변경 사항을 확인한 뒤, 문제가 없으면 승인하고 병합한다.

## 6. Code Review란?

Code Review는 코드를 병합하기 전에 함께 확인하는 과정이다.

코드 리뷰를 하는 이유는 다음과 같다.

- 버그를 예방할 수 있다.
- 코드 품질을 유지할 수 있다.
- 팀 규칙을 공유할 수 있다.
- 더 나은 구현 방식을 논의할 수 있다.
- 코드 변경 이유를 팀원들이 이해할 수 있다.

코드 리뷰의 기본 원칙은 다음과 같다.

- 사람보다 코드 중심으로 리뷰한다.
- 왜 수정이 필요한지 이유를 남긴다.
- 무조건 비판하기보다 개선 방향을 제안한다.
- 승인 후 병합한다.

좋은 리뷰 예시는 다음과 같다.

```text
이 부분은 함수로 분리하면 재사용성이 좋아질 것 같습니다.
```

좋지 않은 리뷰 예시는 다음과 같다.

```text
이거 이상해요.
```

코드 리뷰는 단순히 틀린 부분을 찾는 과정이 아니라, 팀 전체의 코드 품질을 높이는 협업 과정이다.

## 7. Issue란?

Issue는 할 일, 버그 리포트, 기능 요청 등을 관리하는 GitHub 기능이다.

Issue를 사용하면 프로젝트에서 해야 할 작업을 체계적으로 관리할 수 있다.

Issue의 예시는 다음과 같다.

- 로그인 오류 수정
- 회원가입 페이지 추가
- README 문서 보완
- 버튼 스타일 수정
- 버그 리포트
- 기능 요청

Pull Request와 Issue를 연결하면 어떤 작업이 어떤 문제를 해결하는지 명확하게 관리할 수 있다.

예를 들어 PR 설명에 다음과 같이 작성할 수 있다.

```text
Resolve: #123
```

이렇게 작성하면 해당 Pull Request가 123번 Issue를 해결한다는 의미가 된다.

## 8. Fork & Clone 협업 흐름

Fork 방식은 원본 저장소에 직접 push 권한이 없을 때 사용하는 협업 방식이다.

흐름은 다음과 같다.

1. 원본 저장소에서 Issue를 확인하거나 생성한다.
2. 원본 저장소를 내 GitHub 계정으로 Fork한다.
3. 내 포크 저장소를 로컬로 Clone한다.

```bash
git clone 내_포크_저장소_URL
```

4. 원본 저장소를 upstream으로 연결한다.

```bash
git remote add upstream 원본_저장소_URL
```

5. 원본 저장소의 최신 코드를 받는다.

```bash
git pull upstream main
```

6. 작업용 브랜치를 생성한다.

```bash
git switch -c feature/add-my-name
```

7. 코드를 수정하고 커밋한다.
8. 내 포크 저장소에 push한다.
9. GitHub에서 원본 저장소로 Pull Request를 보낸다.

Fork 방식은 오픈소스 프로젝트에 기여할 때 자주 사용된다.

## 9. Collaborator 협업 흐름

Collaborator 방식은 원본 저장소에 직접 협업자로 등록되어 작업하는 방식이다.

팀 프로젝트에서 많이 사용하는 방식이다.

흐름은 다음과 같다.

1. Repository collaborator로 등록된다.
2. Branch protection rules를 설정한다.
3. 원본 저장소를 Clone한다.

```bash
git clone 원본_저장소_URL
```

4. 새로운 브랜치를 생성한다.

```bash
git switch -c feature/mybranch
```

5. 작업 후 커밋한다.

```bash
git commit -m "message"
```

6. 원격 브랜치에 push한다.

```bash
git push origin feature/mybranch
```

7. GitHub에서 Pull Request를 생성한다.

```text
feature/mybranch → main
```

Branch protection rules를 사용하면 main 브랜치에 바로 push하지 못하게 막고, 반드시 PR과 리뷰를 거치도록 설정할 수 있다.

## 10. git show

`git show`는 특정 커밋 하나를 집중해서 살펴볼 때 사용하는 명령어다.

확인할 수 있는 내용은 다음과 같다.

- 해당 커밋의 변경 내용
- diff 정보
- 커밋 메시지
- 작성자
- 날짜

최신 커밋을 확인하려면 다음 명령어를 사용한다.

```bash
git show
```

또는 다음과 같이 쓸 수도 있다.

```bash
git show HEAD
```

특정 커밋을 확인하려면 커밋 해시를 사용한다.

```bash
git show 커밋해시
```

코드 리뷰를 하거나 과거 변경 이력을 자세히 확인할 때 유용하다.

## 11. git diff

`git diff`는 두 상태 간의 차이점을 비교해서 보여주는 명령어다.

커밋 전에 변경 내용을 점검하거나, 병합과 충돌의 원인을 분석할 때 사용한다.

기본 사용법은 다음과 같다.

```bash
git diff
```

이 명령어는 Working Directory와 Staging Area의 차이를 보여준다.

Staging Area와 마지막 커밋 사이의 차이를 보려면 다음 명령어를 사용한다.

```bash
git diff --staged
```

두 커밋 사이의 차이를 비교하려면 다음과 같이 작성할 수 있다.

```bash
git diff HEAD~1 HEAD
```

정리하면 다음과 같다.

| 명령어 | 비교 대상 |
|---|---|
| `git diff` | Working Directory ↔ Staging Area |
| `git diff --staged` | Staging Area ↔ HEAD |
| `git diff HEAD~1 HEAD` | 이전 커밋 ↔ 현재 커밋 |

## 12. git blame

`git blame`은 파일의 각 줄이 누가, 언제, 어떤 커밋에서 수정됐는지 추적하는 명령어다.

예시는 다음과 같다.

```bash
git blame main.py
```

이 명령어를 사용하면 `main.py`의 각 줄마다 수정한 사람과 커밋 정보를 확인할 수 있다.

주로 다음과 같은 상황에서 사용한다.

- 버그 원인을 추적할 때
- 특정 코드가 왜 작성됐는지 확인할 때
- 변경 이력을 자세히 살펴볼 때

단, `blame`은 사람을 탓하기 위한 도구라기보다 코드의 맥락을 이해하기 위한 도구로 사용하는 것이 좋다.

## 13. git stash

`git stash`는 현재 작업 중인 변경 사항을 임시로 치워두는 명령어다.

아직 커밋하기 애매한 작업이 있는데 급하게 다른 브랜치로 이동해야 할 때 유용하다.

현재 작업을 임시 저장하려면 다음 명령어를 사용한다.

```bash
git stash
```

저장된 stash 목록을 확인하려면 다음과 같이 입력한다.

```bash
git stash list
```

가장 최근 stash를 다시 적용하고 목록에서 제거하려면 다음 명령어를 사용한다.

```bash
git stash pop
```

stash를 제거하지 않고 적용만 하려면 다음 명령어를 사용한다.

```bash
git stash apply
```

정리하면 다음과 같다.

| 명령어 | 의미 |
|---|---|
| `git stash` | 현재 변경 사항을 임시 저장 |
| `git stash list` | 저장된 stash 목록 확인 |
| `git stash pop` | 최근 stash 적용 후 목록에서 제거 |
| `git stash apply` | stash를 제거하지 않고 적용만 함 |

## 14. git reset

`git reset`은 브랜치의 기준을 과거 커밋으로 이동시키는 명령어다.

주의할 점은 `reset`은 Git 히스토리를 바꿀 수 있다는 것이다.  
특히 협업 중인 브랜치에서 사용할 때는 조심해야 한다.

대표 옵션은 다음과 같다.

### --soft

커밋만 취소하고 변경 내용은 유지한다.

```bash
git reset --soft HEAD~1
```

이 명령어는 HEAD를 한 커밋 이전으로 이동시키지만, 변경 내용은 그대로 유지한다.

### --mixed

기본 옵션이다.  
커밋과 스테이징을 취소하지만 변경 파일은 Working Directory에 남긴다.

```bash
git reset HEAD~1
```

### --hard

커밋, 스테이징, 파일 변경 내용까지 모두 되돌린다.

```bash
git reset --hard HEAD~1
```

`--hard`는 작업 내용이 사라질 수 있으므로 특히 주의해야 한다.

| 옵션 | 의미 |
|---|---|
| `--soft` | 커밋만 취소, 변경 내용 유지 |
| `--mixed` | 커밋과 스테이징 취소, 파일 변경은 유지 |
| `--hard` | 커밋, 스테이징, 파일 변경까지 모두 되돌림 |

## 15. git revert

`git revert`는 특정 커밋을 되돌리는 새 커밋을 생성하는 명령어다.

```bash
git revert 커밋해시
```

`reset`이 히스토리를 바꾸는 방식이라면, `revert`는 기존 기록을 유지하면서 “이 커밋을 취소했다”는 새 기록을 남긴다.

따라서 협업 중인 브랜치에서는 `reset`보다 `revert`가 더 안전한 경우가 많다.

특징은 다음과 같다.

- 기존 기록을 그대로 유지한다.
- 되돌리는 새 커밋을 만든다.
- 협업 중 안전하게 롤백할 때 사용한다.

## 16. git commit --amend

`git commit --amend`는 마지막 커밋을 수정하는 명령어다.

가장 최근 커밋을 새 커밋으로 교체한다.

사용 예시는 다음과 같다.

```bash
git commit --amend
```

이 명령어를 사용하면 마지막 커밋 메시지를 수정할 수 있다.

기존 커밋 메시지는 그대로 유지하고, 추가 변경 파일만 마지막 커밋에 포함하고 싶다면 다음 명령어를 사용할 수 있다.

```bash
git commit --amend --no-edit
```

사용 가능한 상황은 다음과 같다.

- 마지막 커밋 메시지를 잘못 작성했을 때
- 마지막 커밋에 파일을 빠뜨렸을 때
- 최근 커밋을 조금 수정하고 싶을 때

단, 이미 원격 저장소에 push한 커밋을 amend하면 히스토리가 바뀌기 때문에 협업 중에는 주의해야 한다.

---

## 17. 핵심 명령어 정리

| 명령어 | 의미 |
|---|---|
| `git remote add origin 원격주소` | 원격 저장소 연결 |
| `git remote -v` | 연결된 원격 저장소 확인 |
| `git push -u origin main` | 로컬 main 브랜치를 원격 저장소에 업로드 |
| `git pull` | 원격 저장소 변경 사항을 로컬에 반영 |
| `git clone 저장소_URL` | 원격 저장소를 로컬로 복사 |
| `git remote add upstream 원본_URL` | 원본 저장소를 upstream으로 연결 |
| `git show` | 최신 커밋 상세 확인 |
| `git show 커밋해시` | 특정 커밋 상세 확인 |
| `git diff` | 작업 디렉터리 변경 사항 확인 |
| `git diff --staged` | 스테이징된 변경 사항 확인 |
| `git blame 파일명` | 각 줄의 수정 이력 확인 |
| `git stash` | 작업 중인 변경 사항 임시 저장 |
| `git stash list` | stash 목록 확인 |
| `git stash pop` | 최근 stash 적용 후 제거 |
| `git reset --soft HEAD~1` | 최근 커밋 취소, 변경 내용 유지 |
| `git reset --hard HEAD~1` | 최근 커밋과 변경 내용 모두 되돌림 |
| `git revert 커밋해시` | 특정 커밋을 되돌리는 새 커밋 생성 |
| `git commit --amend` | 마지막 커밋 수정 |

## 18. 전체 흐름 정리

GitHub 협업 흐름은 크게 두 가지 방식으로 나눌 수 있다.

### 팀 내부 협업

```text
원본 저장소에 collaborator 등록
→ clone
→ branch 생성
→ 작업 후 commit
→ push
→ Pull Request 생성
→ Code Review
→ merge
```

### 오픈소스 협업

```text
원본 저장소 Fork
→ 내 저장소 clone
→ upstream 연결
→ 최신 코드 pull
→ branch 생성
→ 작업 후 commit
→ 내 저장소에 push
→ 원본 저장소로 Pull Request 생성
```

두 방식 모두 공통적으로 브랜치를 만들고, 작업 후 Pull Request를 통해 리뷰와 검증을 거친 뒤 병합한다.


# HTML / CSS 1일차 정리

## 1. 수업 개요

이번 수업에서는 웹 화면을 구성하는 기본 기술인 HTML과 CSS의 기초를 학습했다.

HTML과 CSS는 웹 페이지를 만들 때 가장 기본이 되는 기술이다.  
HTML은 웹 페이지의 구조를 만들고, CSS는 그 구조에 디자인과 스타일을 적용한다.

이번 수업의 목표는 HTML과 CSS의 기본 문법을 이해하고, Bootstrap을 활용해 간단한 웹 화면을 직접 구성하는 방법을 배우는 것이다.

주요 내용은 다음과 같다.

- HTML 기초
- CSS 기초
- Bootstrap 기초

---

## 2. HTML이란?

HTML은 HyperText Markup Language의 약자다.  
웹 페이지의 구조를 정의하는 언어다.

HTML은 웹 페이지에서 다음과 같은 요소의 뼈대를 만든다.

- 제목
- 문단
- 이미지
- 링크
- 버튼
- 목록
- 입력창
- 표

즉, HTML은 웹 페이지의 내용을 브라우저가 이해할 수 있도록 구조화하는 역할을 한다.

예를 들어 블로그 글을 작성한다고 하면, 글 제목은 제목 태그로, 본문은 문단 태그로, 이미지는 이미지 태그로 표현할 수 있다.

---

## 3. 웹과 HTML의 관계

웹 서비스에서 서버는 HTML 문서를 만들어 브라우저에 전달할 수 있다.

브라우저는 전달받은 HTML 문서를 읽고, 화면의 기본 구조를 그린다.

흐름은 다음과 같다.

```text
서버
→ HTML 문서 전달
→ 브라우저가 HTML 해석
→ 화면 구조 생성
```

즉, 사용자가 웹 페이지를 열면 브라우저는 서버에서 받은 HTML을 읽고 화면에 표시한다.

HTML은 이때 화면의 기본 뼈대를 담당한다.

---

## 4. HTML 기본 구조

HTML 문서는 항상 일정한 기본 틀을 가진다.

HTML은 태그들의 조합으로 구성된다.  
태그는 보통 다음과 같은 형태로 작성한다.

```html
<태그이름>내용</태그이름>
```

대부분의 태그는 여는 태그와 닫는 태그로 이루어진다.

예시는 다음과 같다.

```html
<h1>제목</h1>
<p>문단 내용</p>
```

여기서 `<h1>`은 제목을 나타내는 태그이고, `<p>`는 문단을 나타내는 태그다.

---

## 5. 태그란?

태그는 HTML에서 요소의 의미와 역할을 나타내는 문법이다.

예를 들어 다음 태그들은 각각 다른 의미를 가진다.

| 태그 | 의미 |
|---|---|
| `<h1>` | 가장 중요한 제목 |
| `<p>` | 문단 |
| `<a>` | 링크 |
| `<img>` | 이미지 |
| `<ul>` | 순서 없는 목록 |
| `<ol>` | 순서 있는 목록 |
| `<li>` | 목록 항목 |
| `<button>` | 버튼 |

HTML에서 중요한 점은 태그가 단순히 모양을 정하는 것이 아니라, 요소의 의미를 표현한다는 것이다.

예를 들어 큰 글씨를 만들고 싶다고 무조건 `<h1>`을 쓰는 것이 아니라, 실제로 페이지의 가장 중요한 제목일 때 `<h1>`을 사용하는 것이 좋다.

---

## 6. HTML 태그의 중첩 구조

HTML 태그 안에는 다른 태그가 들어갈 수 있다.  
이런 구조를 중첩 구조라고 한다.

예시는 다음과 같다.

```html
<body>
  <h1>제목</h1>
  <p>내용</p>
</body>
```

위 코드에서 `<body>` 태그 안에 `<h1>` 태그와 `<p>` 태그가 들어 있다.

이처럼 HTML 문서는 태그들이 계층적으로 포함되는 구조를 가진다.  
브라우저는 이 계층 구조를 해석해서 화면을 만든다.

---

## 7. 기본 HTML 문서 예시

간단한 HTML 문서 예시는 다음과 같다.

```html
<!DOCTYPE html>
<html>
  <head>
    <meta charset="UTF-8">
    <title>나의 첫 웹 페이지</title>
  </head>
  <body>
    <h1>안녕하세요</h1>
    <p>HTML을 배우는 중입니다.</p>
  </body>
</html>
```

각 부분의 의미는 다음과 같다.

| 코드 | 의미 |
|---|---|
| `<!DOCTYPE html>` | 이 문서가 HTML5 문서임을 선언 |
| `<html>` | HTML 문서 전체를 감싸는 태그 |
| `<head>` | 문서 정보가 들어가는 영역 |
| `<meta charset="UTF-8">` | 문자 인코딩 설정 |
| `<title>` | 브라우저 탭에 표시되는 제목 |
| `<body>` | 실제 화면에 보이는 내용 |

---

## 8. CSS란?

CSS는 Cascading Style Sheets의 약자다.  
HTML로 만든 구조에 스타일을 적용하는 언어다.

HTML이 웹 페이지의 뼈대라면, CSS는 디자인을 담당한다.

CSS로 할 수 있는 일은 다음과 같다.

- 글자 색 변경
- 글자 크기 조절
- 배경색 설정
- 요소의 너비와 높이 설정
- 여백 조절
- 테두리 설정
- 배치 조정
- 반응형 화면 구성

예를 들어 HTML로 제목과 문단을 만들었다면, CSS를 사용해 제목의 색상, 글자 크기, 문단 간격 등을 설정할 수 있다.

---

## 9. HTML과 CSS의 역할 차이

HTML과 CSS는 역할이 다르다.

| 구분 | 역할 |
|---|---|
| HTML | 웹 페이지의 구조와 내용 작성 |
| CSS | 웹 페이지의 스타일과 레이아웃 설정 |

예를 들어 집을 짓는다고 생각하면 HTML은 기둥, 벽, 방 구조를 만드는 역할이고, CSS는 벽지, 색상, 가구 배치처럼 꾸미는 역할에 가깝다.

간단히 정리하면 다음과 같다.

```text
HTML = 구조
CSS = 디자인
```

---

## 10. CSS 기본 예시

CSS는 HTML 태그에 스타일을 적용할 수 있다.

예시는 다음과 같다.

```html
<h1>안녕하세요</h1>
<p>HTML과 CSS를 배우는 중입니다.</p>
```

여기에 CSS를 적용하면 다음과 같이 쓸 수 있다.

```css
h1 {
  color: blue;
  font-size: 32px;
}

p {
  color: gray;
  line-height: 1.6;
}
```

위 CSS의 의미는 다음과 같다.

- `h1` 태그의 글자 색을 파란색으로 설정한다.
- `h1` 태그의 글자 크기를 32px로 설정한다.
- `p` 태그의 글자 색을 회색으로 설정한다.
- `p` 태그의 줄 간격을 1.6으로 설정한다.

---

## 11. CSS를 적용하는 방법

CSS를 HTML에 적용하는 방법은 대표적으로 세 가지가 있다.

### 1. 인라인 스타일

HTML 태그 안에 직접 style 속성을 작성하는 방식이다.

```html
<h1 style="color: blue;">제목</h1>
```

간단하지만 스타일이 HTML 코드 안에 섞이기 때문에 유지보수에는 좋지 않다.

### 2. 내부 스타일

HTML 문서의 `<style>` 태그 안에 CSS를 작성하는 방식이다.

```html
<head>
  <style>
    h1 {
      color: blue;
    }
  </style>
</head>
```

하나의 HTML 파일 안에서 간단히 스타일을 적용할 때 사용할 수 있다.

### 3. 외부 스타일시트

별도의 `.css` 파일을 만들고 HTML에서 연결하는 방식이다.

```html
<link rel="stylesheet" href="style.css">
```

실제 프로젝트에서는 외부 CSS 파일을 사용하는 방식이 가장 많이 사용된다.

---

## 12. Bootstrap이란?

Bootstrap은 웹 화면을 빠르게 만들 수 있도록 도와주는 CSS 프레임워크다.

기본 버튼, 카드, 네비게이션 바, 폼, 그리드 시스템 같은 UI 요소를 미리 제공한다.

Bootstrap을 사용하면 CSS를 처음부터 직접 많이 작성하지 않아도 기본적인 디자인이 적용된 화면을 만들 수 있다.

Bootstrap의 장점은 다음과 같다.

- 빠르게 웹 화면을 만들 수 있다.
- 미리 만들어진 UI 컴포넌트를 사용할 수 있다.
- 반응형 레이아웃을 쉽게 구성할 수 있다.
- 디자인 일관성을 유지하기 쉽다.
- 초보자도 보기 좋은 화면을 빠르게 만들 수 있다.

---

## 13. Bootstrap 사용 예시

Bootstrap을 사용하면 버튼도 간단하게 만들 수 있다.

```html
<button class="btn btn-primary">버튼</button>
```

여기서 `btn`과 `btn-primary`는 Bootstrap이 미리 정의해둔 클래스다.

직접 CSS를 많이 작성하지 않아도 Bootstrap 클래스만 사용해서 스타일이 적용된다.

예를 들어 카드 형태의 UI도 Bootstrap을 이용하면 쉽게 만들 수 있다.

```html
<div class="card">
  <div class="card-body">
    <h5 class="card-title">카드 제목</h5>
    <p class="card-text">카드 내용입니다.</p>
  </div>
</div>
```

---

## 14. HTML, CSS, Bootstrap의 관계

HTML, CSS, Bootstrap의 관계는 다음과 같이 정리할 수 있다.

| 구분 | 역할 |
|---|---|
| HTML | 화면의 구조와 내용을 만든다 |
| CSS | 화면의 스타일과 레이아웃을 꾸민다 |
| Bootstrap | 자주 쓰는 CSS 스타일과 컴포넌트를 미리 제공한다 |

즉, HTML로 뼈대를 만들고, CSS로 꾸미고, Bootstrap으로 더 빠르게 화면을 구성할 수 있다.

---

## 15. 전체 흐름 정리

간단한 웹 화면을 만드는 흐름은 다음과 같다.

```text
HTML로 구조 작성
→ CSS로 스타일 적용
→ Bootstrap으로 UI 구성 속도 향상
→ 브라우저에서 결과 확인
```

예를 들어 자기소개 페이지를 만든다면 다음과 같은 순서로 작업할 수 있다.

1. HTML로 제목, 문단, 이미지, 링크를 만든다.
2. CSS로 글자 크기, 색상, 여백을 조절한다.
3. Bootstrap으로 버튼이나 카드 UI를 적용한다.
4. 브라우저에서 화면을 확인한다.
