## 1. 이 노트북이 다루는 문제

이 노트북은 사람의 운동 영상에서 스쿼트 횟수를 자동으로 세는 문제를 다룬다. 핵심 아이디어는 다음 순서다.

1. 영상 또는 CSV에서 사람의 관절 위치를 얻는다.
2. 관절 위치를 그대로 쓰지 않고 무릎 각도로 바꾼다.
3. 각도 시계열을 이용해 앉았다가 일어서는 패턴을 찾는다.
4. 그 과정에서 생기는 노이즈를 스무딩으로 줄여본다.
5. 스무딩과 임계값이 카운팅 정확도에 어떤 영향을 주는지 실험한다.

즉, 이 노트북은 "딥러닝 모델을 쓰는 법"보다 "딥러닝 출력값을 후처리해서 실제 문제를 푸는 법"에 더 가깝다.

## 2. 먼저 알아야 할 기초 개념

### 2.1 Pose Estimation

Pose Estimation은 사람의 몸에서 주요 관절 위치를 찾는 작업이다. YOLO Pose는 한 프레임에서 사람의 어깨, 팔꿈치, 엉덩이, 무릎, 발목 같은 점들을 좌표로 예측한다.

이 과제에서는 COCO 17개 키포인트 체계를 사용한다. 스쿼트 카운팅에는 그중 오른쪽 엉덩이, 오른쪽 무릎, 오른쪽 발목이 중요하다.

- `12`: 오른엉덩이
- `14`: 오른무릎
- `16`: 오른발목

### 2.2 Feature

모델이 바로 "스쿼트 1회"를 주는 것이 아니다. 키포인트 좌표를 받아서 우리가 원하는 정보로 바꿔야 한다. 이때 좌표에서 계산한 무릎 각도가 핵심 feature다.

좌표 대신 각도를 쓰는 이유는 명확하다.

- 사람 위치가 화면 왼쪽인지 오른쪽인지와 무관하다.
- 카메라와의 거리 변화에 덜 민감하다.
- 키가 다른 사람도 "얼마나 굽혔는가"는 비슷한 의미로 비교 가능하다.

### 2.3 시계열 신호

영상은 프레임들의 연속이다. 각 프레임마다 무릎 각도를 계산하면 숫자가 시간 순서대로 쌓인다. 이것이 각도 시계열이다. 스쿼트를 반복하면 이 시계열은 내려갔다가 올라오는 파형을 반복한다.

### 2.4 노이즈

실제 모델 출력은 완벽하지 않다. 같은 자세여도 프레임마다 키포인트가 조금씩 흔들린다. 그러면 각도도 미세하게 흔들린다. 이 잔떨림이 노이즈다.

노이즈가 문제인 이유는 카운터가 임계값을 기준으로 동작하기 때문이다. 신호가 임계값 근처에서 떨리면 실제 한 번의 동작을 여러 번으로 잘못 셀 수 있다.

### 2.5 스무딩

스무딩은 신호를 부드럽게 만드는 전처리다. 이 노트북은 이동평균을 사용한다. 어떤 프레임의 값을 주변 여러 프레임 평균으로 바꿔서 급격한 튐을 줄인다.

하지만 스무딩이 무조건 좋지는 않다.

- 너무 약하면 노이즈가 남는다.
- 너무 강하면 진짜 동작 변화까지 뭉개진다.

이 균형을 찾는 것이 과제 핵심이다.

### 2.6 임계값과 hysteresis

스쿼트 카운트는 단순히 "각도가 작아졌다"만 보면 안 된다. 내려갔다가 다시 올라와야 1회다. 그래서 이 노트북은 두 개의 임계값을 쓴다.

- `down_thr`: 충분히 앉았다고 판단하는 기준
- `up_thr`: 다시 충분히 일어났다고 판단하는 기준

이렇게 두 개를 두면 신호가 중간에서 흔들려도 중복 카운팅이 줄어든다. 이것이 hysteresis 아이디어다.

핵심 내부 함수:

```python
def _angle_from_row(row, triple):
    ...
```

이 함수는 한 행에서 세 관절 좌표를 꺼내 각도를 계산한다.

계산 순서는 이렇다.

1. `kp12_x`, `kp12_y` 같은 좌표를 읽는다.
2. 세 점 `a`, `b`, `c`를 만든다.
3. `b`를 꼭짓점으로 하는 각도를 계산한다.

각도 계산은 벡터 내적 공식을 쓴다.

```python
ba = a - b
bc = c - b
cos = np.dot(ba, bc) / (np.linalg.norm(ba) * np.linalg.norm(bc) + 1e-6)
angle = np.degrees(np.arccos(np.clip(cos, -1.0, 1.0)))
```

여기서 중요한 포인트:

- `np.dot`: 두 벡터의 내적
- `np.linalg.norm`: 벡터 길이
- `1e-6`: 0으로 나누는 문제 방지
- `np.clip`: 부동소수점 오차로 `arccos` 입력이 범위를 벗어나는 것 방지
- `np.degrees`: 라디안을 도 단위로 변환

이 셀 실행 결과:

- 프레임 수: `360`
- 정답 횟수: `8`
- 각도 범위: `98.9 ~ 180.0도`

이 숫자는 곧바로 해석할 수 있다.

- 총 360프레임짜리 데이터다.
- 무릎이 거의 펴졌을 때 180도에 가깝다.
- 가장 많이 굽힌 지점은 약 99도 수준이다.

### 셀 13: 스무딩 설명

이 셀은 이동평균을 사용할 것과, 너무 큰 윈도우는 오히려 문제를 만들 수 있다는 점을 미리 알려준다.

### 셀 14: `moving_average()`

```python
def moving_average(x, window):
```

이 함수는 시계열 `x`에 이동평균을 적용한다.

핵심 코드:

```python
kernel = np.ones(window) / window
padded = np.pad(x, (window//2, window//2), mode='edge')
smoothed = np.convolve(padded, kernel, mode='same')
```

각 줄의 의미:

- `np.ones(window) / window`: 평균용 필터 생성
- `np.pad(..., mode='edge')`: 양 끝에서 값 부족 문제 보정
- `np.convolve`: 필터를 적용해 평균 계산

`window=1`이면 원본 그대로 반환한다. 그래서 `window=1`은 "스무딩 없음"을 의미한다.

같은 셀에서 `raw`와 `smoothed(w=5)`를 같이 그려 비교한다. 여기서 학생은 "스무딩이 노이즈를 줄이되 전체 파형은 유지하는지"를 눈으로 확인할 수 있다.

### 셀 15: 상태머신 카운터 설명

이 셀은 카운터가 단순 비교가 아니라 상태 전환으로 동작한다는 점을 소개한다.

- 처음 상태는 `up`
- 각도가 충분히 낮아지면 `down`
- 다시 충분히 올라오면 `up`으로 복귀하면서 1회 증가

이 구조 때문에 "내려갔다가 다시 올라오는 운동 1사이클"을 셀 수 있다.

### 셀 16: `count_reps()`

```python
def count_reps(angle_series, down_thr, up_thr):
```

이 함수는 각도 신호를 입력받아 횟수를 센다.

작동 방식:

1. 시작 상태는 `up`
2. 각도가 `down_thr`보다 작아지면 `down`
3. 그 뒤 각도가 `up_thr`보다 커지면 다시 `up`이 되며 카운트 `+1`

즉, "한 번 앉고 한 번 일어남"을 1회로 보는 구조다.

이 셀에서는 기본 threshold도 설정한다.

```python
DOWN_THR, UP_THR = 120, 150
```

이번 CSV 데이터 기준에서는 이 값이 가장 적절했다.

실행 결과:

```python
[raw 신호] 카운트 = 8 / 정답 = 8
```

이 결과는 raw 신호만으로도 이미 정답을 맞췄다는 뜻이다. 즉, 노이즈는 있었지만 threshold가 적절해서 카운팅에는 치명적이지 않았다.

### 셀 17: RQ2, RQ3 실험 설명

이 셀은 스무딩 윈도우를 바꾸면서 정확도를 비교하라는 지시다.

- RQ2: 스무딩 없을 때 오차
- RQ3: 스무딩을 달리했을 때 오차 변화

평가 지표는 `abs(pred - truth)`다.

### 셀 18: 윈도우별 반복 실험

```python
windows = [1, 3, 5, 7, 9, 11, 15, 21]
```

이 셀은 각 윈도우 크기에 대해 같은 실험을 반복한다.

매 반복마다:

1. `moving_average(raw_angles, w)`로 스무딩
2. `count_reps()`로 횟수 계산
3. 정답과의 절대오차 계산
4. `(window, count, error)` 저장

실행 결과 표:

```text
window | predicted | abs_error
1      | 8         | 0
3      | 8         | 0
5      | 8         | 0
7      | 8         | 0
9      | 8         | 0
11     | 8         | 0
15     | 4         | 4
21     | 0         | 8
```

이 표는 매우 중요하다. 해석은 다음과 같다.

- `1~11`: 스무딩을 조금 줘도 성능이 유지된다.
- `15`: 너무 많이 부드럽게 해서 반 정도만 감지한다.
- `21`: 거의 동작이 사라져 카운트를 못 한다.

### 셀 19: 결과 그래프와 best window 탐색

이 셀은 두 개의 그래프를 그린다.

1. 윈도우별 예측 횟수
2. 윈도우별 절대 오차

또한 다음 코드로 최적 윈도우를 찾는다.

```python
best = min(results, key=lambda r: r[2])
```

의미:

- `results` 안에서
- 세 번째 값인 `오차`가 가장 작은 항목 선택

실행 결과:

```text
가장 오차가 작은 윈도우: w=1 (예측 8, 오차 0)
```

엄밀히 말하면 `1, 3, 5, 7, 9, 11`이 모두 오차 0이다. 다만 `min()`은 첫 번째 최소값을 반환하므로 `w=1`이 선택된 것이다. 이 점은 코드 해석에서 중요하다.

### 셀 20: 결과 해석 마크다운

이 셀은 이미 실험 결과를 문장으로 정리한다. 핵심 메시지는 세 가지다.

- raw 신호만으로도 정확히 맞춤
- 약한 스무딩은 문제 없음
- 과도한 스무딩은 오히려 성능 악화

즉, 이번 데이터에서는 "노이즈 제거"보다 "신호 보존"이 더 중요했다.

### 셀 21: RQ4 설명

이번에는 스무딩을 고정하고 threshold만 바꾼다. 목적은 카운팅이 threshold 설정에 얼마나 민감한지 확인하는 것이다.

### 셀 22: threshold 민감도 실험

```python
down_candidates = [70, 80, 90, 100, 110, 120]
```

실험 순서:

1. `best_w`로 스무딩 고정
2. `down_thr`만 여러 값으로 바꿔봄
3. 각 값마다 카운트와 오차 계산

실행 결과:

```text
70  -> 0회, 오차 8
80  -> 0회, 오차 8
90  -> 0회, 오차 8
100 -> 1회, 오차 7
110 -> 6회, 오차 2
120 -> 8회, 오차 0
```

해석:

- threshold가 너무 낮으면 "충분히 앉았다"고 거의 판정하지 못한다.
- 그래서 운동을 덜 세게 된다.
- 이번 데이터에서는 `120도`가 가장 적절하다.

그래프는 threshold가 적절한 구간에 들어왔을 때 오차가 급격히 줄어드는 모습을 보여준다.

### 셀 23: 결론 정리

이 셀은 앞선 실험을 보고서 문장으로 정리한 부분이다.

핵심 결론:

- 노이즈는 실제로 존재한다.
- 하지만 이번 데이터에서는 raw 신호만으로도 정답 8회를 맞췄다.
- 작은 스무딩은 성능 유지, 큰 스무딩은 성능 악화
- `down=120`, `up=150`이 가장 적절했다.

또한 "생각해보기" 문항 답안이 함께 들어 있다.

## 6. 이번 실행 결과를 어떻게 해석해야 하나

이번 실행 결과는 단순히 "스무딩이 좋다"가 아니라 더 미묘하다.

### 6.1 RQ1 해석

그래프를 보면 각도는 스쿼트 동작에 맞춰 반복적으로 내려갔다가 올라온다. 확대 구간에서는 프레임 단위 잔떨림이 보인다. 따라서 노이즈는 존재한다.

### 6.2 RQ2 해석

raw 신호 카운트가 `8`이고 정답도 `8`이다. 즉, 노이즈가 존재해도 이번 데이터에서는 정확도 저하로 이어지지 않았다.

이 결과가 중요한 이유는, 노이즈가 보인다고 해서 항상 후처리가 필요한 것은 아니라는 점을 보여주기 때문이다. 신호 크기와 threshold가 적절하면 raw만으로도 충분할 수 있다.

### 6.3 RQ3 해석

`window=1~11`은 모두 완벽했다. 하지만 `15`, `21`에서는 성능이 무너졌다. 이는 스무딩이 너무 강하면 동작 파형의 봉우리와 골짜기가 약해져 카운터가 움직임 자체를 놓칠 수 있음을 의미한다.

즉, 이 실험의 교훈은 다음과 같다.

- 전처리는 필요할 수 있다.
- 하지만 무조건 강하게 하면 안 된다.
- 노이즈 제거와 동작 보존 사이에 trade-off가 있다.

### 6.4 RQ4 해석

threshold는 매우 민감했다. `down_thr`가 너무 낮으면 스쿼트를 제대로 앉은 것으로 판정하지 못해 카운트가 크게 줄었다. 이번 데이터에서는 `120도`가 안정적인 값이었다.

즉, 실제 현장에서는 스무딩만큼 threshold tuning도 중요하다.

## 7. 이 노트북으로 배워야 할 실무 감각

이 노트북은 단순한 입문 과제가 아니라 컴퓨터 비전 파이프라인의 축약판이다.

### 7.1 모델 출력은 끝이 아니다

YOLO Pose는 관절 좌표를 줄 뿐이다. 실제 문제 해결은 그 뒤에 시작된다.
